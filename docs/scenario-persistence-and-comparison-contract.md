## 1. Audited invariants and current behavior

- `apps/web/src/data/ArtifactContext.tsx`: Provider stores one applied `Scenario` and one numeric `PilotInputDraft` in React memory. It independently manages analyst Data Requests, Brief-selected request IDs, checkbox-selected Local Context, and one Pilot-used local indicator. On load it initializes validated reviewed national/local artifacts and illustrative defaults. **No session/local storage currently exists**.
- `apps/web/src/pages/PilotPage.tsx`, `data/pilotInputDraft.ts`: An editable invalid draft is not applied. Valid numeric edits replace the applied scenario immediately; results and sensitivity use only the applied, validated scenario. Target step/mechanism exist in the `Scenario` but are not presently editable in the Pilot form.
- `packages/contracts/src/index.ts`, `packages/scenario-engine/src/index.ts`: `Scenario` has a `scenario_id`, eight numeric planning fields, `target_pathway_step`, `mechanism`, `assumption_refs`, and `artifact_version`. `calculateScenario` validates inputs and finite output; results are deterministic (reach/capacity, person-month planning exposure, program resources), never causal ROI/savings.
- `packages/acquisition-hints/src/dataRequestTemplates.ts`: sensitivity request IDs are global to the session and field (`session.sensitivity.<field>`), not version-scoped. Currency is checked by exact content against `createSensitivityDataRequest(appliedScenario,field)`; mismatches are stale. Other request IDs are not subjected to this sensitivity freshness check.
- `apps/web/src/data/localContextSelection.ts`, `pilotLocalContextSelection.ts`: Pilot-used context is a single `{artifactVersion, indicatorId}` selection, separate from Brief checkbox selections. Resolution requires same current reviewed artifact version and a released record in `loaded` or `partial` state. The Brief unions both record sets and deduplicates by indicator ID.
- `reviewedArtifact.ts`, `reviewedLocalContext.ts`, `reviewedLocalContextValidation.ts`: runtime loads specific reviewed artifact versions with explicit compatibility checks, including a **finite allowlist** for national/local MEPS pairings. A saved scenario has no authority to load an arbitrary prior candidate, supersede review, or promote evidence.
- `apps/web/src/pages/BriefPage.tsx`, `packages/brief-core/src/index.ts`: canonical current Brief is built from the *current* reviewed source, one applied valid scenario, independently selected local indicators, and current selected Data Requests. The Brief builder filters reviewed/released content, sanitizes/resolves optional acquisition guidance, and rechecks sensitivity requests during serialization. JSON and browser print/PDF reflect the same composed Brief. The `generated_at` timestamp remains stable across non-substantive UI changes. Phase 1 must preserve this behavior, including AI handoff.

Important identity distinction: `Scenario.artifact_version` currently identifies the **planning-assumptions version** (`planning-assumptions-2026-09-v1` in defaults); it is **not** the national MEPS artifact version. A persistence contract must store these separately.

## 2. Proposed versioned contract

New pure, runtime-validated `ScenarioVersion` contract (types below are normative shapes, **not deployed code**). For each explicit creation of a logical family or immutable version, use an independent UUID v4 from the browser's cryptographically secure `crypto.randomUUID()`; obtain a fresh candidate on *every* attempt and reject collisions with **all currently retained** family/version IDs in the target catalog and any catalog involved in a scope transfer. Cap attempts at 8 and fail closed if secure randomness is unavailable or collisions persist: no timestamp/counter fallback, no overwrites and no falsely reported save. IDs are opaque, never names, array positions, timestamps, or hashes of editable assumptions. **No intentional ID recycling.** Because deleted IDs are not retained forever, global lifetime uniqueness after deletion cannot be guaranteed; negligible-probability historic collisions are explicitly a residual risk, not a promise of impossible reuse.

```ts
type ScenarioId = string; // "scn_" + UUID, unique for a logical scenario
type ScenarioVersionId = string; // "scv_" + UUID, unique immutable snapshot

type PilotContextReference =
  | { state: "selected"; artifactVersion: string; indicatorId: string }
  | { state: "none"; artifactVersion: string }
  | { state: "unavailable"; artifactVersion: null };

interface ScenarioSourceIdentity {
  planningAssumptionsVersion: string; // equals snapshot.scenario.artifact_version
  calculationContractVersion: string; // explicitly published engine arithmetic contract
  nationalArtifactVersion: string;   // actual reviewed bundle.manifest.artifact_version
  nationalCodeCommit: string;        // bundle.manifest.code_commit, source attribution
  localArtifactVersion: string | null; // actual reviewed artifact, if loaded
}

interface ScenarioVersion {
  schemaVersion: 1;
  scenarioId: ScenarioId;
  versionId: ScenarioVersionId;
  revision: number;                   // 1,2,3... within this scenario family
  parentVersionId: ScenarioVersionId | null;
  savedAt: string;                    // validated ISO 8601 UTC
  nameAtSave: string;                 // historical label, immutable
  duplicationOrigin?: {              // immutable, non-authoritative lineage metadata
    sourceScenarioId: ScenarioId;     // may be deleted later; no required live reference
    sourceVersionId: ScenarioVersionId;
    mode: "full-copy" | "historical-inputs-only";
  };
  snapshot: {
    scenario: Scenario;              // all 8 numeric inputs, pathway, mechanism,
                                     // assumption_refs, planning artifact version
    pilotContext: PilotContextReference;
    sources: ScenarioSourceIdentity;
  };
}
interface ScenarioFamily {
  scenarioId: ScenarioId;
  currentName: string;               // rename metadata only
  createdAt: string;
  versionIds: ScenarioVersionId[];   // ordered immutable version records
}
interface ScenarioCatalogV1 {
  catalogSchemaVersion: 1;
  catalogRevision: number;           // storage conflict/stale-tab detection
  families: ScenarioFamily[];
  versions: ScenarioVersion[];
  // No unbounded retiredScenarioIds/tombstone collection: see deletion policy below.
}
```

**Cross-field validation:** exact known keys; no prototype-pollution/unknown nested fields; bounded catalog/labels/arrays/bytes; UUID-form and uniqueness; valid dates; `revision` sequential and distinct within family; parent belongs to the same family, points backward, and is acyclic; `versionId` and family `scenarioId` unique within their respective namespaces; `snapshot.scenario.scenario_id === scenarioId`; planning version equals `snapshot.sources.planningAssumptionsVersion`; valid `Scenario` via `validateScenario`, **plus** finite result via `calculateScenario`; valid path/mechanism and arrays; pilot context reference consistency; source identity nonempty; supported schema and calculation contract. If `duplicationOrigin` exists, validate its exact keys, UUID-shaped IDs and enumerated mode; it is historical traceability only, **not** authority to retrieve a source, imply current eligibility, or require an undeleted source record. Validate snapshot `scenarioId` binding independently. Do not trust parsed storage because it is local.

**Calculation contract authority (proposed implementation, not present in current runtime):** Add and export a reviewed, code-owned constant `SCENARIO_CALCULATION_CONTRACT_VERSION = "pilot-deterministic-v1"` from `packages/scenario-engine/src/index.ts` (or a tightly coupled pure `scenario-engine` module that it exports). This version represents *numeric/semantic computation and validation behavior*, not a user-supplied value, a package version, a saved field, or a Git/source commit. During **save**, obtain `snapshot.sources.calculationContractVersion` only from that imported constant, and obtain national/local artifact identities only from the validated runtime loaders. During **restore**, read the constant from the **currently running** `scenario-engine`, compare it to the syntactically valid stored version, and **block activation** on any mismatch/unknown version, even for inputs-only restore; never select an engine implementation based on storage. Equality is only a necessary compatibility check, **not evidence of provenance/authenticity** of tamperable browser data. Independently validate saved `Scenario`, exact catalog/schema/source consistency, and recalculate the result with the current engine. Do not claim cryptographic attestation of a locally stored snapshot.

A change to rounding, bounds, numeric validation, formulae, field semantics, outputs, or the scientific meaning of a result **requires** a deliberate calculation-contract-version bump, golden fixture/result review against both old and new behavior, and an explicit release/compatibility decision in the *same reviewed change*. Build-time golden-fixture and version-bump/behavior-change checks should fail on semantic drift with an unchanged version; code review is still necessary because a finite golden suite cannot prove all semantics. A future migration/compatibility adapter may only be added under separate approval and must never silently recalculate older snapshots as equivalent. Cosmetic UI copy/style changes or unrelated build SHA changes do not trigger a calculation-contract bump.

**What is stored:** immutable, finite analyst inputs and their scientific boundary; selected Pilot-used indicator **identifier only**, with local artifact identity; the national artifact used when saved; assumption refs; schema/model identities; audit timestamps. **What is not stored:** reviewed estimate/indicator bodies, raw source data, evidence records or effect parameters, acquired hints, session Data Request bodies or Brief selections, calculator result caches as truth, AI-generated statements, patient data, browser download objects.

- Recompute `ScenarioResult` from validated inputs using the same deterministic engine on restore/compare. Never deserialize a stored result as authoritative. Golden-result tests must pin calculation semantics.
- No automatic version when editing, navigating, printing, changing selections, or autosaving a draft. The illustrative default is never silently added to the library.
- A logical `ScenarioId` persists across explicit revisions and rename. `versionId` is immutable. **Duplicate is a library-only operation** that creates a new family and revision-1 version with new opaque IDs, and **never** activates or rebinds the applied workspace. Its complete classification, historical-source handling, confirmation and error semantics are specified in **§3, Duplicate protocol**. The optional, immutable `duplicationOrigin` object above records non-authoritative traceability without requiring retention of a subsequently deleted source.
- First `Save as new scenario` assigns a fresh logical ID. **After confirmed successful durable write**, explicit activation atomically rebinds `Scenario.scenario_id` to the new family ID, recalculates `ScenarioResult.scenario_id`, and records the active saved version **without changing the eight numeric assumptions, pathway, or mechanism**; if persistence fails, leave the applied identity and Brief untouched. Show the identity change and its Brief consequences before confirmation. Subsequent `Save new version` preserves the family ID, increments revision, and captures currently applied assumptions. No change to applied state is necessary for version-only save when its inputs/identity are already current. All snapshots are immutable.
- Rename updates `ScenarioFamily.currentName` only, leaving saved `nameAtSave`, `versionId`, timestamps and computations unchanged. A save after rename records the new name. Display both current and historical labels where they differ.
- Delete asks for confirmation; removes the family and all its versions from the *chosen scope* in a validated bounded catalog transaction and drops Phase 2 comparison selections referencing them. **Do not write or grow `retiredScenarioIds`** or retain deletion tombstones indefinitely. Fresh cryptographic allocation with active-ID collision checks replaces any promise of perfect post-deletion lifetime uniqueness. Deleted IDs are not intentionally reassigned or restored; IDs in untouched catalogs/scopes remain unchanged. The applied workspace and unrelated Data Requests/Brief checkbox selections remain unchanged; after a **confirmed** delete of the active version show **unsaved/unlinked workspace** rather than silently clearing inputs. A rejected or **uncertain** delete must not change the *last confirmed in-memory* library or claim completion; **never promise the original persisted bytes survived an uncertain write or another tab**. An uncertain delete enters read-only reconciliation as defined in §3. No undo guarantee without an explicit previously exported backup.

## 3. Persistence, migration and transaction boundaries

Phase 1 supports an explicitly chosen browser scope: **session-only** (default; `sessionStorage`) or **keep on this device** (`localStorage`, affirmative opt-in). Browser storage is best effort and is not encrypted, synced, backed up, or suitable for patient identifiers. Scenario names should be short and avoid sensitive content. Never imply cross-device availability.

- One prefixed, schema-versioned **bounded** catalog envelope per active scope; no mixing or silent merging between stores. Switching scope previews target occupancy and explicitly requires move/copy/conflict choice. A move only reports success after destination validation/read-back **and** verified source removal; if source removal is rejected, report **destination copy confirmed / move incomplete**, with original source status not guaranteed until independently re-read. If source removal is **uncertain**, freeze destructive writes in the affected scope(s) and reconcile both independently; never assert the source is still present or run automatic compensating overwrites. ID collisions and differing records between scopes **block implicit merge/overwrite**; even identical IDs are not silently coalesced. Deletion in one scope does not delete a corresponding entry in another. No tombstone is required or fabricated on scope switch; fresh IDs are collision-checked against retained records in both catalogs before new copies/duplicates.
- On initialization, first load the reviewed artifacts/current planning defaults **exactly as today**. Independently parse/validate the saved *library*; do not auto-restore the latest scenario or make it the default Brief. A corrupt/unsupported library cannot displace default state.
- Preflight validation, serialize-to-memory, write, read-back and verify before reporting success. **Proposed hard v1 caps (enforce for each scope on load/migration/write):** at most **50 scenario families**, **50 versions per family**, **250 versions total**, **80 Unicode code points** for a trimmed display name, **32 assumption refs per version** (each at most **256 Unicode code points**), and **512 KiB** maximum UTF-8 serialized catalog payload. Reject oversized/unparseable imported catalogs rather than truncating them; actual browser storage quotas vary, so the cap does **not** guarantee a write will succeed. Caps are not an automatic eviction or retention policy: when full, offer an explicit analyst-chosen delete/export-and-delete workflow or fail the save without losing unrelated versions/records. **Deleting a family removes its records but creates no tombstones**; no separate retired-ID budget can grow. On preflight or write/quota/security/private-mode exceptions, retain the **last independently validated in-memory catalog** and leave workspace activation unchanged; report only the appropriate outcome defined below, **not** success. In particular, an unverified post-write result is **not** proof of unchanged persisted bytes. Treat storage operations as an adapter with injectable before-write, write-throw, after-write/read-back, and concurrent-writer fault points.
- Fresh install (`catalogSchemaVersion` absent) creates an empty catalog **only after an explicit save**; there is no legacy saved-schema source to import. Any future v1→vN migration must be explicit, deterministic/idempotent, validated before commit, preserve source/IDs **without inventing recycled IDs or unbounded tombstones**, and retain a recovery copy until success. A migration that exceeds the target size/count budget is **blocked with the original still recoverable**, not auto-pruned or partially committed. Unknown **future** versions and malformed payloads are read-only/unavailable; never overwrite or silently reset them. User-directed export/recovery is preferable to silent deletion.
- `catalogRevision` and `storage` events are **best-effort conflict indicators**, not a cross-tab lock. Validate the observed revision and selected exact records again immediately before writes or workspace confirmation; invalidate stale previews and refuse operations after an observed conflict. Web Storage does **not** give a fully atomic cross-tab compare-and-swap: even a successful compare/read-back can race another tab; do not promise globally conflict-free edits. For enforceable multi-tab transactions, upgrade to an IndexedDB transactional store before claiming concurrent editing safety.
- Use no default or incidental telemetry of scenario content. No remote persistence or auto-sync in this phase.

### Storage operation outcomes, uncertain writes and nondestructive recovery (G-I2)

All catalog mutations (**Save as New/version, Duplicate, Rename, Delete, scope copy/move, and migration**) use one explicit operation-outcome contract. The word **confirmed** means that the mutation was successfully invoked and an independently decoded, strict-schema-valid **exact expected catalog** was read back from the intended scope, with expected catalog revision, IDs, record content and serialized equality checked. A confirmed read-back is still **not** a cross-tab linearizable transaction.

| Outcome | Observable boundary | In-memory / user-visible behavior |
| --- | --- | --- |
| `NOT_ATTEMPTED` | Preflight validation, quota-budget check, stale-revision check, target-source compatibility or user confirmation fails **before calling any mutator** | No write from this operation; no active workspace, confirmed catalog or UI success mutation; show actionable validation/conflict error. Does **not** assert another tab made no write. |
| `WRITE_REJECTED` | Storage mutator throws, e.g. quota/security/permission exception, with **no acknowledged successful write** | Show write failure, leave the last confirmed in-memory catalog and applied workspace unchanged. Browser failure may not establish persisted byte identity; if an adapter could have changed storage before throwing, or verification cannot exclude that, classify as `UNCERTAIN` instead. Recheck storage before any subsequent retry. |
| `CONFIRMED` | Mutator returns successfully; subsequent fresh read exactly matches intended bounded catalog, including revision/contents, and validates | Only now advance the last confirmed in-memory catalog and report saved/deleted/duplicated/renamed (or complete scope-move after **both** operations confirmed). Save as New may now activate; Duplicate **never** does. A later conflicting tab can still change storage. |
| `UNCERTAIN` | Mutator may have committed, **including success followed by failed/denied/corrupt read-back, mismatched read-back, or an observed concurrent modification**; also any mutator error with ambiguous side effects | **Do not** claim saved/deleted/moved or that old bytes remain. Keep the **last independently validated in-memory catalog snapshot** as the only last-known state, do not adopt an unverified candidate, and keep the current applied Pilot/Brief unchanged. Enter read-only conflict/reconciliation mode: block subsequent **destructive or mutating** catalog actions (including deletes, saves, duplicates, scope moves and migrations) until resolved. |

**Reconciliation is nondestructive and explicit:** Surface `result uncertain — storage may have changed`, last confirmed revision/scope and the intended operation; keep the last confirmed catalog accessible as a **read-only preview** and, where feasible, allow user-controlled export of its validated data (not a guarantee of current storage contents). On user-initiated retry of **read only**, fetch and validate the **entire** persisted catalog and revision without writing: (1) exact last confirmed snapshot means the operation cannot be certified as applied; (2) exact intended post-operation snapshot may be offered as **reconciled after independent verification**, never silently called originally confirmed; (3) a valid third state/changed revision requires a visible conflict choice, read-only inspection and explicit acceptance of the observed catalog after preserving/exporting the local known state; (4) unreadable, invalid, unsupported or repeatedly failing storage stays **read-only/blocked** with recovery/export guidance. Explicit acceptance switches the in-memory confirmed view to a newly validated persisted state; **never** silently merge catalogs, treat an old in-memory snapshot as proof of persisted bytes, or automatically roll back/overwrite possibly concurrent edits. A new save is permitted only after conflict state is fully resolved and fresh preflight is performed. On a concurrent write even after a successful read-back, display newly observed divergence on the next revision check; irreducible races remain a v1 limitation.

### Duplicate protocol (G-I1) — library only, never activation

1. **Select/preview:** User selects a specific existing `scenarioId + versionId` in one storage scope and enters a **new name**. Snapshot current catalog revision, exact immutable selected version content, historical source versions and selected Pilot-used reference; show original saved date separately from **new duplication date**. Display `Duplicate creates a saved library copy; it will not open, activate or change your current Pilot or Planning Brief`. An unsaved/invalid Pilot draft is irrelevant because Duplicate reads the **saved** version, not working inputs.
2. **Validate/classify using the Restore gates:** Strictly validate source version identity, current authoritative `SCENARIO_CALCULATION_CONTRACT_VERSION`, saved version/Scenario inputs and finite recalculated result; resolve both reviewed national and local source identities **against current validated runtime loaders and compatibility allowlist**, and resolve the Pilot-used indicator by exact current artifact/version, release and eligibility. **Block** if schema/source metadata malformed, saved engine version is unknown/incompatible, scenario is invalid/nonfinite, source family/version has changed/deleted, catalog is conflicted/uncertain or fresh secure IDs cannot be allocated. A saved value never authorizes an older engine or unreviewed source.
3. **Compatible original:** When saved sources and Pilot context are currently eligible, offer **Duplicate reviewed-compatible snapshot**. Allocate an independently new `scn_` ID and `scv_` ID (revision 1, `parentVersionId: null`, new `savedAt`, chosen `nameAtSave`/`currentName`) and set `snapshot.scenario.scenario_id` to the **new family ID**. Preserve all other numeric/qualitative assumptions, `assumption_refs`, original `Scenario.artifact_version`, `snapshot.pilotContext` and **every `snapshot.sources` source identifier byte-for-byte**. Set `duplicationOrigin: { sourceScenarioId, sourceVersionId, mode: "full-copy" }`. This is a new saved *copy of the historical attribution*, **not** a fresh review/certification.
4. **Old/incompatible reviewed source or Pilot context:** If the authoritative **engine contract and numeric snapshot are valid**, but the historical national/local source version is no longer the currently eligible source, an allowlist pairing fails, or the indicator is missing, suppressed, preliminary or release-ineligible, present a **separate explicit** `Duplicate historical inputs only` choice with the exact mismatches and warning: **historical source/indicator IDs will be retained for provenance but are NOT attached, reviewed or eligible in the current runtime**. Confirmation creates a **library-only** clone with the *same original source identities and Pilot reference kept as historical, unresolved metadata* and `duplicationOrigin.mode: "historical-inputs-only"`; no new reviewed evidence is assigned and no Pilot-used indicator becomes active. This designation is not a license to use the historical reference in Brief; a future Restore still independently checks eligibility and may only perform its separately confirmed **inputs-only restore**, which clears the live Pilot selection. **Never stamp the current national/local version or calculation version onto the historical duplicate**, silently remap indicators, or present `savedAt` as a source-review date. If the user does **not** expressly confirm the historical-inputs-only caveat, cancel without writing.
5. **Confirm and commit:** Immediately before **any write**, re-read the selected scope, require unchanged `catalogRevision`, revalidate exact selected immutable version bytes/identity (or stable semantic digest), current engine version, reviewed artifacts/allowlist, indicator eligibility and classification; re-check current destination catalog budgets, UUID collisions and scope/operation state. If anything changed since preview, **invalidate the confirmation**, show new status and require a fresh preview/explicit decision. Write only the new family/version catalog transaction, classify via G-I2 outcome/read-back. On `CONFIRMED`, add the copy to the library with link to new card. On any other outcome, **no activation**, preserve applied scenario, numeric draft, results, Pilot-used local context, independent Brief checkbox selections, Data Requests, Brief JSON/print and `generated_at`; uncertain writes require reconciliation before trying again. Never automatically chain Duplicate → Restore or Duplicate → Save as New.
6. **Accessibility:** Confirmation and failure messages distinguish `copied`, `not copied`, and `could have been copied; verify storage`; return keyboard focus to the initiating Duplicate control if it still exists, otherwise the new/selected library card heading or saved-scenario list heading, **never `BODY`**. Use an accessible status/alert, preserve user-entered name and preview context after validation failure, and leave recovery actions keyboard-operable. A library-only copy must not steal focus to Pilot or Brief.

## 4. Controlled restore protocol (pure dry-run then explicit commit)

1. User selects an exact **scenarioId + versionId**, previews name, date, eight inputs, pathway/mechanism, provenance, local reference, and differences from current applied inputs. Warn if current draft has incomplete/unapplied edits; require explicit discard confirmation.
2. Validate catalog/version identity, saved scenario, calculation result, and source identity. Independently obtain the **authoritative calculation-contract version from currently executing `scenario-engine` code**. A missing/forged/unknown stored version, or a stored version unequal to the current runtime constant, **blocks** even inputs-only restore (absent a separately reviewed future compatibility adapter); neither a familiar label nor a saved version proves compatibility. Resolve current reviewed national and local artifacts **through existing loaders/validators**, not stored source payloads; check same exact versions and existing allowed cross-artifact compatibility.
3. Classify a restore: **full** (schema/engine and all selected references compatible and eligible); **inputs-only, explicit** (calculation contract compatible but a reviewed source or selected Pilot-used reference is missing/changed/ineligible); **blocked** (invalid record, unsupported schema/calculation contract, or invalid/nonfinite scenario).
4. **At actual confirmation, not only at preview open:** Re-read/revalidate the chosen scope, require the same `catalogRevision`, `scenarioId + versionId` and **exact immutable selected snapshot** as previewed; recheck current **code-owned calculation-contract version**, finite result under running engine, reviewed national/local artifacts, compatibility allowlist and release/eligibility of the exact Pilot indicator. Ensure no concurrent/uncertain catalog state. If selected version, catalog revision, engine, source/release status or predicted **full vs inputs-only vs blocked** classification has changed, **cancel the prior confirmation** and require a new preview and explicit informed decision; never accept the prior inputs-only checkbox for newly different mismatches. This is a best-effort recheck, not an atomic cross-tab lock.
5. Only after successful confirmation-time validation, full restore **commits a single workspace transaction** (one reducer action, never three independently visible setters) applying the validated `scenario`, matching `createPilotInputDraft(scenario)`, and the reviewed Pilot-used context selection (or explicit `none`). Prepare the entire transaction before dispatch so neither Brief nor sensitivity explorer observes mixed old/new state. Inputs-only restore clears/unattaches **only** Pilot-used context in the applied workspace, preserves a visible unresolved-reference warning and the immutable saved reference, and requires user confirmation. If a stored indicator has become `preliminary`, `unavailable`, `suppressed`, or changed artifact version, **never** substitute another indicator with the same label.
6. **Do not mutate** Local Context Brief checkbox selections, `analystDataRequests`, `briefDataRequestIds`, reviewed bundles, evidence, or acquisition hints. After **any** applied-scenario identity/value change, including Save as New and Restore, **derive** freshness against the newly applied scenario (rerun `isDataRequestCurrentForScenario` and the existing Brief/acquisition eligibility gates) before composition/serialization; do not reuse cached freshness from a previous identity. Current sensitivity request IDs (`session.sensitivity.<field>`) and match logic are **content-based**, not bound to `scenario_id`: changing only the ID **does not automatically make a request stale** if its required generated contents still match. Conversely, changes to any relevant numeric, pathway or mechanism values must exclude stale selected sensitivity requests with the existing warning until explicit refresh. Preserve the selected request IDs and records even when excluded. Existing non-sensitivity requests are not newly certified as scenario-applicable merely by restoring. The existing reviewed hint resolver still independently verifies any optional guidance.
7. Recompute the canonical current one-scenario Brief from its **unchanged Phase 1 composition rules** using the new applied `Scenario` and recomputed result. `Scenario.scenario_id` is already serialized in `brief.scenario.input`; `ScenarioResult.scenario_id` is already serialized in `brief.scenario.result`. Save as New and Restore can therefore change **canonical Brief JSON content and bytes**, even if all eight numerical inputs and model outputs other than identity are unchanged. Never include a restored scenario or local ref in export solely because it was stored. Save/restore dialogs must accurately distinguish a recorded source version from the *currently loaded* source.

### Brief identity, recomposition and `generated_at` (Phase 1 contract)

- Preserve the existing single-scenario `PlanningBrief` **schema, canonical encoder, filtering, print layout, and composition rules**. Do **not** claim byte-for-byte parity before/after an intentional `scenario_id` change or a source/selection mutation. A restored version may also change numeric outputs and eligibility of selected sensitivity requests. The JSON and printed Brief should represent the **same newly composed scientific state**, while acknowledging their distinct formats.
- `BriefPage` currently memoizes canonical Brief construction on the applied `scenario`, `scenarioResult`, reviewed bundle/context, selected local records and selected/current Data Requests. `buildPlanningBrief` supplies `generated_at` when it constructs a new Brief. A scenario-ID rebind **is a substantive composition change**: invalidate memoized Brief/handoff/source signatures and generate a fresh timestamp from a test-injected clock. Do not preserve the old timestamp as though content were unchanged; do not promise two calls can never share a millisecond in real time. A version-only library save or rename without any applied/Brief inputs changing does not require recomposition.
- Printing, opening disclosures, and changing the **print-only local appendix detail toggle** must not recompose the canonical Brief; with a frozen composition clock and unchanged scenario identity, inputs, source and selections, the **serialized canonical JSON stays byte-identical**. The print-only toggle is permitted to change **PDF detail/page count**, so no PDF byte-identical promise applies across different print choices. JSON byte comparisons always operate on the same memoized Brief; freshly constructed Briefs will have their own timestamps.
- Apply the scenario identity/draft/result transaction atomically and rerun content-based sensitivity-request freshness before export. Show `Scenario.scenario_id` / selected version identity in the Save/Restore confirmation and warn that the Planning Brief may change (including `generated_at`, scenario identifiers, request eligibility and its JSON companion). No automatic Data Request rewriting, unreviewed artifact adoption, or indirect promotion of local evidence.

If national runtime context changes, an inputs-only restore reuses **only analyst assumptions**; it does not assert original evidence continuity. The next explicit save may capture the new active source identity as a new revision after user review. A `partial` local record is selectable only when its **reviewed release status and current artifact eligibility** pass existing gates; do not conflate the record's `partial` data state with a *partial restore*.

## 5. Phase 1 UX flow

- Pilot → **Saved scenarios** (initially empty, clearly labeled browser/session scope).
- Applied, valid draft: **Save as new** (name required, explicit confirmation), or when associated with a family: **Save new version**. Invalid draft or numeric overflow: saving blocked; preview shows last applied values versus draft.
- Library cards: name, latest revision, saved date, source/compatibility status; expandable version history with **Preview / Restore / Duplicate / Rename / Delete**. Clear distinctions between working changes, last applied result, and immutable versions.
- Restore preview: side-by-side input changes and explicit full/inputs-only/blocked state; if context is unresolved show precise artifact and indicator IDs and the effect of proceeding. **Revalidate at confirm**; on changed version/revision/runtime sources, cancel stale confirmation, retain original applied state and give a fresh review option.
- Duplicate preview: library-only new family, with either compatible-copy or explicitly confirmed **historical-inputs-only** classification; separate old source provenance from copy date and do not advertise a duplicate as activated. Failed/uncertain writes leave the applied Brief unchanged.
- Each action has a precise accessible confirmation/status/error; no automatic "best" label, no excessive alerts, keyboard and screen-reader support, and no silent overwrite of a different browser scope. On success/cancel/error/conflict, return focus to an existing action trigger or meaningful surviving library heading; never drop keyboard focus to `BODY`. For uncertainty, show a screen-reader-announced read-only status, last-confirmed revision and keyboard-accessible **retry read / compare / export last-confirmed snapshot / explicitly accept verified recovery** controls. ## 8. Risks, decisions requiring approval, and phased engineering

**PM approved in principle (pending independent G and final contract disposition):** (A) Session-only by default with explicit local-device opt-in; (B) new logical ID + immutable per-save version ID; (C) Save New activates/rebinds the saved family without numeric changes, **thereby changing Brief identity/content** after successful persistence; (D) explicit inputs-only restore on reviewed source mismatch, **blocked** for unsupported calculation-contract versions; (E) no Data Request or Brief checkbox snapshot/restore; (F) Phase 1 Brief **schema/composition contract** unchanged, **not its JSON bytes** after substantive identity/content changes; (G) no Web Storage cross-tab CAS promise; (H) bounded catalog with cryptographically fresh IDs, collision retry and **no unbounded retired-ID history**.
