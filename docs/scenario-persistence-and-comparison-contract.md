## 1. Audited invariants and current behavior

- `apps/web/src/data/ArtifactContext.tsx`: Provider stores one applied `Scenario` and one numeric `PilotInputDraft` in React memory. It independently manages analyst Data Requests, Brief-selected request IDs, checkbox-selected Local Context, and one Pilot-used local indicator. On load it initializes validated reviewed national/local artifacts and illustrative defaults. **No session/local storage currently exists**.
- `apps/web/src/pages/PilotPage.tsx`, `data/pilotInputDraft.ts`: An editable invalid draft is not applied. Valid numeric edits replace the applied scenario immediately; results and sensitivity use only the applied, validated scenario. Target step/mechanism exist in the `Scenario` but are not presently editable in the Pilot form.
- `packages/contracts/src/index.ts`, `packages/scenario-engine/src/index.ts`: `Scenario` has a `scenario_id`, eight numeric planning fields, `target_pathway_step`, `mechanism`, `assumption_refs`, and `artifact_version`. `calculateScenario` validates inputs and finite output; results are deterministic (reach/capacity, person-month planning exposure, program resources), never causal ROI/savings.
- `packages/acquisition-hints/src/dataRequestTemplates.ts`: sensitivity request IDs are global to the session and field (`session.sensitivity.<field>`), not version-scoped. Currency is checked by exact content against `createSensitivityDataRequest(appliedScenario,field)`; mismatches are stale. Other request IDs are not subjected to this sensitivity freshness check.
- `apps/web/src/data/localContextSelection.ts`, `pilotLocalContextSelection.ts`: Pilot-used context is a single `{artifactVersion, indicatorId}` selection, separate from Brief checkbox selections. Resolution requires same current reviewed artifact version and a released record in `loaded` or `partial` state. The Brief unions both record sets and deduplicates by indicator ID.
- `reviewedArtifact.ts`, `reviewedLocalContext.ts`, `reviewedLocalContextValidation.ts`: runtime loads specific reviewed artifact versions with explicit compatibility checks, including a **finite allowlist** for national/local MEPS pairings. A saved scenario has no authority to load an arbitrary prior candidate, supersede review, or promote evidence.
- `apps/web/src/pages/BriefPage.tsx`, `packages/brief-core/src/index.ts`: canonical current Brief is built from the *current* reviewed source, one applied valid scenario, independently selected local indicators, and current selected Data Requests. The Brief builder filters reviewed/released content, sanitizes/resolves optional acquisition guidance, and rechecks sensitivity requests during serialization. JSON and browser print/PDF reflect the same composed Brief. The `generated_at` timestamp remains stable across non-substantive UI changes. Phase 1 must preserve this behavior, including AI handoff.

Important identity distinction: `Scenario.artifact_version` currently identifies the **planning-assumptions version** (`planning-assumptions-2026-09-v1` in defaults); it is **not** the national MEPS artifact version. A persistence contract must store these separately.

## 2. Proposed versioned contract

New pure, runtime-validated `ScenarioVersion` contract (types below are normative shapes, **not deployed code**). For each explicit creation of a logical family or immutable version, use an independent UUID v4 from the browser's cryptographically secure `crypto.randomUUID()`; obtain a fresh candidate on *every* attempt and reject collisions with **all currently retained** family/version IDs in the target catalog and any catalog involved in a scope transfer. Cap attempts at 8 and fail closed if secure randomness is unavailable or collisions persist: no timestamp/counter fallback, no overwrites and no falsely reported save. IDs are opaque, never names, array positions, timestamps, or hashes of editable assumptions. **No intentional ID recycling.** Because deleted IDs are not retained forever, global lifetime uniqueness after deletion cannot be guaranteed; negligible-probability historic collisions are explicitly a residual risk, not a promise of impossible reuse.

```ts
type ScenarioId = string; // "scn_" + UUID, unique for a logical scenario
type ScenarioVersionId = string; // "scv_" + UUID, unique immutable snapshot

type PilotContextReference =
  | { state: "selected"; artifactVersion: string; indicatorId: string }
  | { state: "none"; artifactVersion: string }
  | { state: "unavailable"; artifactVersion: null };

interface ScenarioSourceIdentity {
  planningAssumptionsVersion: string; // equals snapshot.scenario.artifact_version
  calculationContractVersion: string; // explicitly published engine arithmetic contract
  nationalArtifactVersion: string;   // actual reviewed bundle.manifest.artifact_version
  nationalCodeCommit: string;        // bundle.manifest.code_commit, source attribution
  localArtifactVersion: string | null; // actual reviewed artifact, if loaded
}

interface ScenarioVersion {
  schemaVersion: 1;
  scenarioId: ScenarioId;
  versionId: ScenarioVersionId;
  revision: number;                   // 1,2,3... within this scenario family
  parentVersionId: ScenarioVersionId | null;
  savedAt: string;                    // validated ISO 8601 UTC
  nameAtSave: string;                 // historical label, immutable
  snapshot: {
    scenario: Scenario;              // all 8 numeric inputs, pathway, mechanism,
                                     // assumption_refs, planning artifact version
    pilotContext: PilotContextReference;
    sources: ScenarioSourceIdentity;
  };
}
interface ScenarioFamily {
  scenarioId: ScenarioId;
  currentName: string;               // rename metadata only
  createdAt: string;
  versionIds: ScenarioVersionId[];   // ordered immutable version records
}
interface ScenarioCatalogV1 {
  catalogSchemaVersion: 1;
  catalogRevision: number;           // storage conflict/stale-tab detection
  families: ScenarioFamily[];
  versions: ScenarioVersion[];
  // No unbounded retiredScenarioIds/tombstone collection: see deletion policy below.
}
```

**Cross-field validation:** exact known keys; no prototype-pollution/unknown nested fields; bounded catalog/labels/arrays/bytes; UUID-form and uniqueness; valid dates; `revision` sequential and distinct within family; parent belongs to the same family, points backward, and is acyclic; `versionId` and family `scenarioId` unique within their respective namespaces; `snapshot.scenario.scenario_id === scenarioId`; planning version equals `snapshot.sources.planningAssumptionsVersion`; valid `Scenario` via `validateScenario`, **plus** finite result via `calculateScenario`; valid path/mechanism and arrays; pilot context reference consistency; source identity nonempty; supported schema and calculation contract. Do not trust parsed storage because it is local.

**Calculation contract authority (proposed implementation, not present in current runtime):** Add and export a reviewed, code-owned constant `SCENARIO_CALCULATION_CONTRACT_VERSION = "pilot-deterministic-v1"` from `packages/scenario-engine/src/index.ts` (or a tightly coupled pure `scenario-engine` module that it exports). This version represents *numeric/semantic computation and validation behavior*, not a user-supplied value, a package version, a saved field, or a Git/source commit. During **save**, obtain `snapshot.sources.calculationContractVersion` only from that imported constant, and obtain national/local artifact identities only from the validated runtime loaders. During **restore**, read the constant from the **currently running** `scenario-engine`, compare it to the syntactically valid stored version, and **block activation** on any mismatch/unknown version, even for inputs-only restore; never select an engine implementation based on storage. Equality is only a necessary compatibility check, **not evidence of provenance/authenticity** of tamperable browser data. Independently validate saved `Scenario`, exact catalog/schema/source consistency, and recalculate the result with the current engine. Do not claim cryptographic attestation of a locally stored snapshot.

A change to rounding, bounds, numeric validation, formulae, field semantics, outputs, or the scientific meaning of a result **requires** a deliberate calculation-contract-version bump, golden fixture/result review against both old and new behavior, and an explicit release/compatibility decision in the *same reviewed change*. Build-time golden-fixture and version-bump/behavior-change checks should fail on semantic drift with an unchanged version; code review is still necessary because a finite golden suite cannot prove all semantics. A future migration/compatibility adapter may only be added under separate approval and must never silently recalculate older snapshots as equivalent. Cosmetic UI copy/style changes or unrelated build SHA changes do not trigger a calculation-contract bump.

**What is stored:** immutable, finite analyst inputs and their scientific boundary; selected Pilot-used indicator **identifier only**, with local artifact identity; the national artifact used when saved; assumption refs; schema/model identities; audit timestamps. **What is not stored:** reviewed estimate/indicator bodies, raw source data, evidence records or effect parameters, acquired hints, session Data Request bodies or Brief selections, calculator result caches as truth, AI-generated statements, patient data, browser download objects.

- Recompute `ScenarioResult` from validated inputs using the same deterministic engine on restore/compare. Never deserialize a stored result as authoritative. Golden-result tests must pin calculation semantics.
- No automatic version when editing, navigating, printing, changing selections, or autosaving a draft. The illustrative default is never silently added to the library.
- A logical `ScenarioId` persists across explicit revisions and rename. `versionId` is immutable. A duplicate starts a *new* scenario family and new version, with cloned assumptions and references subject to validation; its provenance can optionally point to the source version as a **non-authoritative** `duplicatedFromVersionId` only if added to the schema through review.
- First `Save as new scenario` assigns a fresh logical ID. **After confirmed successful durable write**, explicit activation atomically rebinds `Scenario.scenario_id` to the new family ID, recalculates `ScenarioResult.scenario_id`, and records the active saved version **without changing the eight numeric assumptions, pathway, or mechanism**; if persistence fails, leave the applied identity and Brief untouched. Show the identity change and its Brief consequences before confirmation. Subsequent `Save new version` preserves the family ID, increments revision, and captures currently applied assumptions. No change to applied state is necessary for version-only save when its inputs/identity are already current. All snapshots are immutable.
- Rename updates `ScenarioFamily.currentName` only, leaving saved `nameAtSave`, `versionId`, timestamps and computations unchanged. A save after rename records the new name. Display both current and historical labels where they differ.
- Delete asks for confirmation; removes the family and all its versions from the *chosen scope* in a validated bounded catalog transaction and drops Phase 2 comparison selections referencing them. **Do not write or grow `retiredScenarioIds`** or retain deletion tombstones indefinitely. Fresh cryptographic allocation with active-ID collision checks replaces any promise of perfect post-deletion lifetime uniqueness. Deleted IDs are not intentionally reassigned or restored; IDs in untouched catalogs/scopes remain unchanged. The applied workspace and unrelated Data Requests/Brief checkbox selections remain unchanged; if the deleted version was active, show **unsaved/unlinked workspace** rather than silently clearing inputs. Failed deletion/partial storage write must preserve the original library and never claim completion; no undo guarantee without an explicit previously exported backup.

## 3. Persistence, migration and transaction boundaries

Phase 1 supports an explicitly chosen browser scope: **session-only** (default; `sessionStorage`) or **keep on this device** (`localStorage`, affirmative opt-in). Browser storage is best effort and is not encrypted, synced, backed up, or suitable for patient identifiers. Scenario names should be short and avoid sensitive content. Never imply cross-device availability.

- One prefixed, schema-versioned **bounded** catalog envelope per active scope; no mixing or silent merging between stores. Switching scope previews target occupancy and explicitly requires move/copy/conflict choice. A move only reports success after destination validation/read-back, then attempts source removal; if source removal fails, report **copy completed / move incomplete** (not a completed move), retain the source and allow safe user resolution. ID collisions and differing records between scopes **block implicit merge/overwrite**; even identical IDs are not silently coalesced. Deletion in one scope does not delete a corresponding entry in another. No tombstone is required or fabricated on scope switch; fresh IDs are collision-checked against retained records in both catalogs before new copies/duplicates.
- On initialization, first load the reviewed artifacts/current planning defaults **exactly as today**. Independently parse/validate the saved *library*; do not auto-restore the latest scenario or make it the default Brief. A corrupt/unsupported library cannot displace default state.
- Preflight validation, serialize-to-memory, write, read-back and verify before reporting success. Specify explicit implementation caps for record count, history depth, field/label lengths and serialized bytes **before writing tests or shipping**; caps are enforceable at each write, no automatic eviction or silent trimming of older versions or other records. When full, offer an explicit analyst-chosen delete/export-and-delete workflow or fail the save, with no lost unrelated data. On write/quota/security/private-mode exceptions, retain in-memory working state, report **not saved**, do not update catalog/selection as persisted. Treat storage updates as an adapter with injectable failing in-memory test doubles.
- Fresh install (`catalogSchemaVersion` absent) creates an empty catalog **only after an explicit save**; there is no legacy saved-schema source to import. Any future v1→vN migration must be explicit, deterministic/idempotent, validated before commit, preserve source/IDs **without inventing recycled IDs or unbounded tombstones**, and retain a recovery copy until success. A migration that exceeds the target size/count budget is **blocked with the original still recoverable**, not auto-pruned or partially committed. Unknown **future** versions and malformed payloads are read-only/unavailable; never overwrite or silently reset them. User-directed export/recovery is preferable to silent deletion.
- `catalogRevision` and `storage` events detect stale tabs and trigger conflict UI; test rejecting writes from an observed stale revision. Web Storage does **not** give a fully atomic cross-tab compare-and-swap: concurrent writers remain a documented risk. For enforceable multi-tab transactions, upgrade to an IndexedDB transactional store before claiming concurrent editing safety. Do not promise guaranteed conflict-free simultaneous writes in v1.
- Use no default or incidental telemetry of scenario content. No remote persistence or auto-sync in this phase.

## 4. Controlled restore protocol (pure dry-run then explicit commit)

1. User selects an exact **scenarioId + versionId**, previews name, date, eight inputs, pathway/mechanism, provenance, local reference, and differences from current applied inputs. Warn if current draft has incomplete/unapplied edits; require explicit discard confirmation.
2. Validate catalog/version identity, saved scenario, calculation result, and source identity. Independently obtain the **authoritative calculation-contract version from currently executing `scenario-engine` code**. A missing/forged/unknown stored version, or a stored version unequal to the current runtime constant, **blocks** even inputs-only restore (absent a separately reviewed future compatibility adapter); neither a familiar label nor a saved version proves compatibility. Resolve current reviewed national and local artifacts **through existing loaders/validators**, not stored source payloads; check same exact versions and existing allowed cross-artifact compatibility.
3. Classify a restore: **full** (schema/engine and all selected references compatible and eligible); **inputs-only, explicit** (calculation contract compatible but a reviewed source or selected Pilot-used reference is missing/changed/ineligible); **blocked** (invalid record, unsupported schema/calculation contract, or invalid/nonfinite scenario).
4. Full restore **commits a single workspace transaction** (one reducer action, never three independently visible setters) applying the validated `scenario`, matching `createPilotInputDraft(scenario)`, and the reviewed Pilot-used context selection (or explicit `none`). Validate and prepare the entire transaction before commit so neither the Brief nor the sensitivity explorer observes mixed old/new state. Inputs-only restore clears/unattaches **only** Pilot-used context in the applied workspace, preserves a visible unresolved-reference warning and the immutable saved reference, and requires user confirmation. If a stored indicator has become `preliminary`, `unavailable`, `suppressed`, or changed artifact version, **never** substitute another indicator with the same label.
5. **Do not mutate** Local Context Brief checkbox selections, `analystDataRequests`, `briefDataRequestIds`, reviewed bundles, evidence, or acquisition hints. After **any** applied-scenario identity/value change, including Save as New and Restore, **derive** freshness against the newly applied scenario (rerun `isDataRequestCurrentForScenario` and the existing Brief/acquisition eligibility gates) before composition/serialization; do not reuse cached freshness from a previous identity. Current sensitivity request IDs (`session.sensitivity.<field>`) and match logic are **content-based**, not bound to `scenario_id`: changing only the ID **does not automatically make a request stale** if its required generated contents still match. Conversely, changes to any relevant numeric, pathway or mechanism values must exclude stale selected sensitivity requests with the existing warning until explicit refresh. Preserve the selected request IDs and records even when excluded. Existing non-sensitivity requests are not newly certified as scenario-applicable merely by restoring. The existing reviewed hint resolver still independently verifies any optional guidance.
6. Recompute the canonical current one-scenario Brief from its **unchanged Phase 1 composition rules** using the new applied `Scenario` and recomputed result. `Scenario.scenario_id` is already serialized in `brief.scenario.input`; `ScenarioResult.scenario_id` is already serialized in `brief.scenario.result`. Save as New and Restore can therefore change **canonical Brief JSON content and bytes**, even if all eight numerical inputs and model outputs other than identity are unchanged. Never include a restored scenario or local ref in export solely because it was stored. Save/restore dialogs must accurately distinguish a recorded source version from the *currently loaded* source.

### Brief identity, recomposition and `generated_at` (Phase 1 contract)

- Preserve the existing single-scenario `PlanningBrief` **schema, canonical encoder, filtering, print layout, and composition rules**. Do **not** claim byte-for-byte parity before/after an intentional `scenario_id` change or a source/selection mutation. A restored version may also change numeric outputs and eligibility of selected sensitivity requests. The JSON and printed Brief should represent the **same newly composed scientific state**, while acknowledging their distinct formats.
- `BriefPage` currently memoizes canonical Brief construction on the applied `scenario`, `scenarioResult`, reviewed bundle/context, selected local records and selected/current Data Requests. `buildPlanningBrief` supplies `generated_at` when it constructs a new Brief. A scenario-ID rebind **is a substantive composition change**: invalidate memoized Brief/handoff/source signatures and generate a fresh timestamp from a test-injected clock. Do not preserve the old timestamp as though content were unchanged; do not promise two calls can never share a millisecond in real time. A version-only library save or rename without any applied/Brief inputs changing does not require recomposition.
- Printing, opening disclosures, and changing the **print-only local appendix detail toggle** must not recompose the canonical Brief; with a frozen composition clock and unchanged scenario identity, inputs, source and selections, the **serialized canonical JSON stays byte-identical**. The print-only toggle is permitted to change **PDF detail/page count**, so no PDF byte-identical promise applies across different print choices. JSON byte comparisons always operate on the same memoized Brief; freshly constructed Briefs will have their own timestamps.
- Apply the scenario identity/draft/result transaction atomically and rerun content-based sensitivity-request freshness before export. Show `Scenario.scenario_id` / selected version identity in the Save/Restore confirmation and warn that the Planning Brief may change (including `generated_at`, scenario identifiers, request eligibility and its JSON companion). No automatic Data Request rewriting, unreviewed artifact adoption, or indirect promotion of local evidence.

If national runtime context changes, an inputs-only restore reuses **only analyst assumptions**; it does not assert original evidence continuity. The next explicit save may capture the new active source identity as a new revision after user review. A `partial` local record is selectable only when its **reviewed release status and current artifact eligibility** pass existing gates; do not conflate the record's `partial` data state with a *partial restore*.

## 5. Phase 1 UX flow

- Pilot → **Saved scenarios** (initially empty, clearly labeled browser/session scope).
- Applied, valid draft: **Save as new** (name required, explicit confirmation), or when associated with a family: **Save new version**. Invalid draft or numeric overflow: saving blocked; preview shows last applied values versus draft.
- Library cards: name, latest revision, saved date, source/compatibility status; expandable version history with **Preview / Restore / Duplicate / Rename / Delete**. Clear distinctions between working changes, last applied result, and immutable versions.
- Restore preview: side-by-side input changes and explicit full/inputs-only/blocked state; if context is unresolved show precise artifact and indicator IDs and the effect of proceeding.
- Each action has a precise accessible confirmation/status/error; no automatic "best" label, no excessive alerts, keyboard and screen-reader support, and no silent overwrite of a different browser scope.
- Phase 1 **does not alter the canonical single-scenario Planning Brief schema, composition rules, print layout, export choices, or AI-handoff schema**. Its **content is not immutable**: an explicit Save as New or Restore changes applied scenario identity and can change canonical JSON bytes, recomposition time, current Data Request status and any resulting export. Review the newly composed Brief before download.

## 6. Phase 2 — comparison and controlled Brief inclusion (separate PM gate)

- Comparison is opt-in, selects **exactly 2 or 3 explicitly saved `versionId`s** (not unsaved drafts or every edit), permits multiple versions of one logical family, and defaults to **none selected**. Explicit selector is independent of restore and independent of current applied Brief scenario.
- Compare every numeric analyst input, target pathway step/mechanism, assumption refs, original source identities, and Pilot-used local context IDs. Show raw values and signed deltas with clearly named **reference scenario** chosen by analyst, not chosen by software.
- Recalculate the **same** existing `ScenarioResult` per saved input and display outputs/deltas including reached participants, intended reach, capacity gap, baseline/alternative/difference person-months, and program resources. No new outcome/effect models, composite score, automatic rank, "winner" or local savings.
- For different `calculationContractVersion`s, show inputs/provenance but **withhold cross-version output deltas** unless an explicitly reviewed compatibility/migration rule exists. For different national/local versions or geographies, display separately with prominent **not directly comparable evidence context** warnings; do not pool, normalize, or imply equivalence. Unsupported or unreviewed context cannot be silently resolved from storage.
- Evidence/assumption status is **per column**, produced from the current reviewed source/admissibility gates; persisted assumption refs do not constitute reviewed evidence. Clearly separate what was assumed, what is currently eligible, and what was unavailable at save time.
- Brief selection: separate explicit **Include this comparison in Planning Brief** control, selecting 2–3 saved version IDs; default off. Keep the existing canonical applied-scenario section unchanged. Only after Phase 2 schema and rendering approval add a separately versioned comparison appendix to both rendered/printed Brief **and** JSON companion, including version IDs, immutable input snapshots, recomputed deterministic results, source-version statuses and incompatibility warnings. Deletion/invalidation of any selected saved version removes or blocks appendix generation with an explicit message, never silently substitutes another version. Source gating and request freshness must run again at composition and serialization. AI handoff adopts any new schema only after separate acceptance; until then it must omit/not invent comparison content and preserve current behavior.

## 7. Deterministic acceptance matrix

Run pure unit/contract tests plus integrated browser, JSON/PDF, accessibility and provenance tests on the exact implementation HEAD, with explicit fixture/source versions:

1. Identity: UUID validity and fresh secure generation; active family/version ID collision retry up to 8 attempts; monotonically increasing revisions per family; immutable snapshots; rename preserves history; duplicate does not deliberately reuse IDs; delete does not affect other families. **Negative:** force duplicate candidates across the currently retained catalog and scope-transfer target; fail after retry exhaustion with no write, no family replaced and no false success. Mock `crypto.randomUUID` absence/error; fail with no fallback. A deleted ID is not retained as an unbounded tombstone: test that later creation does not *intentionally* recycle it and document why historical collisions after deletion cannot be ruled out by a bounded browser store.
2. Input validity: each numeric field, reach bounds, alternative ≤ baseline window, NaN/Infinity/unsafe derived overflow, malformed strings, missing schema, unknown keys, forged IDs, inconsistent parent chain, mismatched `Scenario.scenario_id` and source identity.
3. Storage: absent/empty storage, corrupt/truncated JSON, unsupported future schema, expired/invalid migration, quota exceeded, denied access, read-back mismatch, interrupted write, attempted silent reset, concurrent-tab stale revision, scope switch with conflicting IDs. **Negative:** fill the bounded catalog and attempt one additional save (must fail, not evict any previous scenario); repeat thousands of save/delete cycles and assert no accumulating tombstones/retired IDs and bounded encoded size; reject a migration that would exceed limits and retain recoverable source; reject a conflicting scope merge without overwriting either catalog; when destination move succeeds but source deletion fails, report incomplete move rather than falsely declaring success. Assert **no false saved/deleted/moved status** and unrelated stored/applied state untouched on failed operations.
4. Save UX: no implicit version on per-keystroke edits, route change, print, selection toggle, or page refresh; invalid draft cannot save; save exactly captures validated applied values including noneditable pathway/mechanism and assumption refs; explicit activation identity behavior. **Negative:** inject a failed Save as New write and assert **no** `Scenario.scenario_id` rebind, result ID change, Brief recomposition or `generated_at` change; on successful save assert new `scenario_id` in both input and result while numeric outputs remain unchanged.
5. Restore: full, none, unavailable and selected Pilot reference; unchanged artifact, rotated local artifact, missing indicator, revoked reviewed release, record `partial` vs ineligible release, unknown national version, incompatible calculation contract, malformed snapshot, simulated missing bundle. **Negative:** runtime `SCENARIO_CALCULATION_CONTRACT_VERSION` = v2 but stored v1; deny full **and** inputs-only restore without touching applied state even if numeric fields pass. Reject missing/unknown/malformed stored version. Forge a saved version label equal to runtime while injecting invalid numeric/source metadata: strict validators or recomputation must still reject, and no claim of historical authenticity may be made. Golden fixtures must catch deliberate rounding/formula/validation drift when the version is not bumped; a properly bumped version must reject old records pending an explicitly reviewed adapter. Assert no reviewed source mutation and no auto-reattachment/substitution.
6. Unrelated state: restore must not change existing analyst request array, request inclusion IDs, acquisition hints, independent Brief checkbox-selected Local Context, or reviewed national/local bundles. **Negative:** Save as New changes only `scenario_id` with otherwise equal template values: recalculate freshness, and verify formerly current requests remain current under existing **content-based** semantics; no blanket invalidation. Restore an earlier version with changed reach/horizon/pathway or mechanism: rerun freshness for all three fields, leave request bodies and selected IDs unchanged, and verify selected stale requests are omitted from JSON/print with warning. After restoring a version whose content genuinely matches an old request, currency may return without mutating the request; do not silently refresh any request.
7. Canonical export: unchanged Phase 1 single-scenario Brief JSON **shape and composition rules**, print/PDF scientific-state parity, no suppressed/unreleased evidence, and unchanged optional acquisition guidance guardrails. **Negative:** compare frozen-clock canonical JSON before and after Save as New with no numeric edits; bytes **must differ** specifically in `scenario.input.scenario_id`, `scenario.result.scenario_id`, and any newly composed `generated_at` (force distinct test clock times); all deterministic non-ID numeric outputs must match. Then Restore an older distinct version, assert IDs (and any changed values) match that version, no stale Brief/handoff cache, and a refreshed composition timestamp. Conversely, given unchanged applied ID, inputs, source and selections, opening disclosures, printing, and toggling print-only appendix detail must leave **canonical JSON byte-identical and `generated_at` stable**; the PDF may differ in included detail/pagination. A version-only save or library rename without applied-state change must not spuriously recompose the Brief.
8. Phase 2 (future): 0/1/2/3/4 selected cases; only 2–3 allowed in comparison, duplicate family versions, explicit reference/delta sign, model/version mismatch withholding output deltas, source incompatibility warnings, deleted/invalid selected ID, inclusion default off, identical JSON+print membership and warnings, no score/ranking and no causal/ROI output.
9. Regression: Pilot draft/results/sensitivity; Local Context → Pilot handoff; all 34 eligible local records and Brief selections; currently reviewed compatibility allowlist; Data Requests; `buildPlanningBrief`/`serializeBriefJson`; AI handoff; print boundary/page rules; workspace accessibility.

## 8. Risks, decisions requiring approval, and phased engineering

**PM approved in principle (pending independent G and final contract disposition):** (A) Session-only by default with explicit local-device opt-in; (B) new logical ID + immutable per-save version ID; (C) Save New activates/rebinds the saved family without numeric changes, **thereby changing Brief identity/content** after successful persistence; (D) explicit inputs-only restore on reviewed source mismatch, **blocked** for unsupported calculation-contract versions; (E) no Data Request or Brief checkbox snapshot/restore; (F) Phase 1 Brief **schema/composition contract** unchanged, **not its JSON bytes** after substantive identity/content changes; (G) no Web Storage cross-tab CAS promise; (H) bounded catalog with cryptographically fresh IDs, collision retry and **no unbounded retired-ID history**.

**Risks:** Identical readable indicator IDs do not establish same reviewed artifact; scenario's planning-artifact version is not MEPS provenance; future calculator changes must use a reviewed **runtime-owned** version constant and semantic goldens; browser storage cannot authenticate version claims; deleted historic IDs cannot be exhaustively checked forever in bounded storage; non-sensitivity requests currently bypass sensitivity freshness logic; Web Storage is not transactional across tabs; local storage is neither private nor reliable backup; existing Brief and AI handoff contracts are single-scenario.

**Post-approval implementation slices (all post-demo):**
1. Contract and pure validated catalog/restore planner, typed calculation version, exhaustive deterministic tests; **no UI/persistence activation**.
2. Injectable browser storage adapters with failures, migrations, scope controls and conflict/error surfacing; security/privacy review.
3. Saved-scenario UI and explicit transaction/restore integration, with independent request/Brief context state unchanged; accessibility and end-to-end regression.
4. Independent Workstream G product acceptance + D release QA, PM go/no-go; only then consider runtime activation/merge/deployment in a future release.
5. Separate Phase 2 design-review and implementation PRs for compare + additive canonical Brief/PDF/JSON inclusion, with the same acceptance gates.

**Definition of ready for Phase 1:** PM signs off this clarified contract and controlled-restore semantics **after independent Workstream G architecture/UX/scientific-boundary review, separately from PR #127's time-sensitive visual acceptance**; exact artifact/version policy and proposed runtime version authority are understood. **Only then request PM authorization** for an isolated post-demo contract/unit-test implementation slice on a separate PR; no Phase 1 runtime code/merge/deploy or Phase 2 activation is authorized by this design PR. No scientific release promotion is implied.
