# Community Pulse S0 closeout and S1 qualification

## Preflight the exact JSON

From the feature worktree, run this command against a private local file.

```sh
node --experimental-strip-types scripts/community-pulse/validate-report.mjs /path/to/report.json
```

Exit code 0 means the real v0.2.1 validator and intake accept the file. Exit code 1 means rejection and exit code 2 means a file or invocation error. The output gives raw byte count for files within the limit, item count, overlength paths and UTF-16 lengths, runtime issues, and the intake disposition. It prints no report content, sends nothing, and creates no durable candidate. The runtime stops validating an array once it exceeds its limit. The CLI can still measure text lengths across that array. Keep actual rejected submissions in private storage outside Git.

The owner-supplied 38,478-byte `on_demand` report was valid JSON and within the 64 KiB transport cap. The strict validator rejected its 30 items, and the intake returned `invalid_report_schema` with zero candidates. Eleven item texts also exceeded 700 UTF-16 code units, with a maximum of 1,022. An agent's declared validity is informational. For the first live email, use the completed synthetic example from the [agent contract](INSTINCT_AGENT_CONTRACT_v0.2.1.md). Set `report_type` to `on_demand`, assign a unique run ID, and preflight the exact JSON before using it as the email body. For research that exceeds the limits, narrow the assignment before generation or record an honest `partial` result describing omitted coverage. Keep the full unsubmitted research private. Preserve qualifiers and completion status.

[Routing subdomains](https://developers.cloudflare.com/email-service/configuration/subdomains/) · [MX onboarding troubleshooting](https://developers.cloudflare.com/email-service/reference/troubleshooting/#onboarding-fails-with-non-cloudflare-mx-records-exist)

In [R2](https://dash.cloudflare.com/?to=/:account/r2/overview) and [Billing](https://dash.cloudflare.com/?to=/:account/billing), confirm R2 eligibility and accept the terms only if the owner authorizes activation. 3. Provide the exact authorized mail hostname and account, and authorize staging-only DNS, Routing, Worker, and R2 operations. The owner can handle DNS in the dashboard and omit those write permissions. For read-only inspection use the corresponding Read scopes plus **Zone Read**, **Zone Settings Read**, and **DNS Read** as applicable. Billing inspection is owner-side or uses separate **Billing Read**. No account master key is needed. [Cloudflare API permissions](https://developers.cloudflare.com/fundamentals/api/reference/permissions/) · [Routing DNS endpoint](https://developers.cloudflare.com/api/resources/email_routing/subresources/dns/methods/create/) · [Exact rule endpoint](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/methods/create/)
4. Follow the existing [Phase S0 deployment and qualification runbook](PHASE_S0.md) after the owner supplies those details and permissions. The Worker begins disabled, with one secret destination and one separate server read credential. Verify Vercel Authentication and the runtime kill switch before intake. The draft changes the nested report contract only. Keep the independently enforced 65,536-byte decoded limit, 256 KiB raw email limit, five source leads per item, normalized R2 object limit of 96 KiB, and 1 MiB Vercel/browser projection cap. Forty ASCII texts of 2,000 units would exceed the decoded byte ceiling before any JSON overhead. Case mix, URL lengths, and UTF-8 byte lengths determine which ceilings are reachable together. The supplied attachment satisfied the draft on-demand shape and existing source-minimum rules in an in-memory check. That confirms compatibility with the example, without accepting or rewriting it.

A local Node timing probe with in-memory R2 ran existing synthetic email intake at a p95 of about 0.9 ms for a 62.8 kB fixture. The existing 10-report inbox response was 632.2 kB and took about 4.0 ms p95 for a changed projection, and 0.03 ms for a conditional hit. A draft 64.7 kB, 40-item shape parsed, validated and hashed in about 0.45 ms p95. That draft measurement covered a narrower code path. These probes do not represent Cloudflare cold starts, production R2, Vercel response cost, browser rendering, or workerd's measured 10 ms Free CPU budget. [Cloudflare Email Worker limits](https://developers.cloudflare.com/email-service/platform/limits/) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

The existing inbox reads, validates, and hashes up to ten full reports when its projection changes. Vercel and the browser validate again. Mobile rendering builds the item rows inside collapsed disclosures. Forty entries with five leads each could yield 400 items and 2,000 leads across ten retained cards. Establish a lightweight summary response and lazy detail before enabling broader payloads. Qualify representative source-heavy, multibyte, just-under and over-cap, and mixed-version requests. Exercise changed and conditional reads, replay, peak memory and CPU in Cloudflare, and keyboard access and opening detail on a representative mobile device. In alternate text formats, include a case where JSON escaping expands the stored wrapper.

If the draft passes those gates, keep the current v0.2.1 validator frozen and dispatch a separate v0.2.2 research body validator by version. Do not bump the shared version used by extraction, snapshots, and inbox envelopes. Deploy browser/Vercel and Worker storage readers before enabling intake of v0.2.2 JSON, and retire any older protected preview readers connected to the same inbox. Do not rewrite existing objects or their digests. Retries keep their exact original report version and run ID. A distinct report version is for new logical runs. Roll back the writer and retain readers for versions already stored.

## Proposed private history and intelligence threads

Use the existing newest-first R2 receipt journal as the history index. List at most 25 projected summary rows per page from a bounded number of R2 pages. Keep the opaque cursor short-lived and signed, and bind it to the filters and a high-water timestamp. Enforce the current retention cutoff and allowlist the date, type, and outcome filters. Deduplicate across appends. Handle expiration between list and detail. Fetch a single report on demand via a trusted lookup of its opaque receipt reference, verifying the content digest. Keep the same protected preview identity, server credential, and private response policy. Automatic refresh should poll summary and health only. Keep pagination position stable and offer a new-deliveries indicator.

Show received reports with substantive items in the default view. Roll up no-change runs in delivery health and make them available in full history. Report the last successful check separately from the last substantive report. Keep quarantines and duplicate receipts in operator diagnostics so hourly activity cannot hide substantive research.

For persistent threads, start with operator-owned R2 records that have opaque IDs, a topic, owner, review status, and an as-of timestamp. Append immutable revisions and update a head pointer conditionally. Store citation edges to receipt ID, report digest, version, and item index. Keep reviewer write access and audit identity separate from intake and the staging reader. When candidate retention expires or access is revoked, mark the reference unavailable. Never duplicate raw content to extend retention. Any future core intelligence engine should use an independently authorized read-only projection of reviewed evidence with revision and withdrawal semantics. Keep the existing Cloudflare and Vercel boundaries and introduce no Google Cloud dependency.

The proposed history and thread model add no database or knowledge graph. They are independent of first-email qualification.
