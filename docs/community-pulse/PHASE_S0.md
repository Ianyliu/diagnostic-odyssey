## Prepare the Cloudflare destination

1. Identify an existing controlled Cloudflare zone and a dedicated unused subdomain, such as `pulse-mail.<owned-domain>`. Obtain the owner's authorization for this zone, new subdomain MX/TXT records, Worker deployment and routing, and a private Standard R2 bucket under permitted billing terms. Confirm the account can use R2 and create its `workers.dev` subdomain. Keep the existing apex and production mail records intact. If onboarding demands changes to existing MX, stop that operation and use a separately controlled eligible zone. [Cloudflare routing subdomains](https://developers.cloudflare.com/email-service/configuration/subdomains/)
2. Enable R2 in the authorized account if terms and eligibility are acceptable. Create a private Standard bucket named `community-pulse-staging-intake`, with public access and all public domain mappings disabled. Configure lifecycle deletion at 30 days for `s0/`, with a two-day lifecycle for `s0/rate/` where supported. See the retention rules below for the progress summary and deletion procedure. [R2 lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)
3. From the tested revision, run `node scripts/community-pulse/build-worker.mjs /absolute/private/path/worker.mjs`. Upload to the staging script `community-pulse-staging` using the Workers API multipart upload with [staging metadata](../../apps/pulse-worker/staging-upload.json) as `metadata` and the bundle as `worker.mjs` with media type `application/javascript+module`. The generated bundle uses the shared runtime validator and `nodejs_compat`. Start with the kill switch off. Enable the account's `workers.dev` endpoint for this script and disable version preview URLs. Confirm the endpoint has the form `https://community-pulse-staging.<account>.workers.dev`. [Cloudflare Workers script upload](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/update/)
4. Generate 16 or more random bytes encoded as 32–48 lowercase hex characters for the private local part, using the operation `openssl rand -hex 16`. Prepend `pulse-` and append `@<dedicated-subdomain>`. Store the full address as secret `PULSE_STAGING_RECIPIENT` and give it only to the project operator and Instinct's native send action. Independently generate a URL-safe read token of 43–128 characters and bind it as `PULSE_INBOX_TOKEN`. Set `PULSE_EXPECTED_SENDER` to the exact owner-confirmed managed address. The optional `PULSE_EXPECTED_ENVELOPE_SENDER` and `PULSE_DKIM_DOMAIN` default to the expected From address and its domain. Override them only after identifying the legitimate envelope identity and domain signer during qualification. A parent signer must be an explicitly configured parent of the From domain.
5. In Cloudflare, select the dedicated subdomain under Email Routing, verify the new MX/TXT records, and add one exact custom-address rule with action **Send to a Worker** for `community-pulse-staging`. Leave catch-all disabled. Leave other addresses and mail workflows alone. Keep the native recurring assignments paused. [Cloudflare Email Routing](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/)
6. Configure only the approved branch in Vercel Preview. Preserve `VITE_COMMUNITY_PULSE_ENABLED=on` and `COMMUNITY_PULSE_MODE=fixture`. Set `PULSE_STAGING_WORKER_URL` to the Worker root and `PULSE_STAGING_WORKER_TOKEN` to the separate Worker read token as a server-side secret. Set `PULSE_STAGING_INBOX_ENABLED=on` for this branch alone. Redeploy the exact reviewed Git revision once to apply the protected preview's configuration. Subsequent arrivals are runtime reads and do not cause builds. [Vercel Preview environment variables](https://vercel.com/docs/environment-variables#preview-environment-variables) · [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication)
7. Once isolation is confirmed and the first synthetic delivery is authorized, switch the Worker to `PULSE_STAGING_ENABLED=on` with the staging configuration. Confirm that anonymous direct Worker requests yield 401, anonymous Vercel HTML and API requests reach Vercel Authentication, and an authorized operator sees an empty staging inbox. Enable the hourly expectation only when the trial starts via `PULSE_HOURLY_EXPECTED_SINCE`, an explicitly chosen UTC instant. No cron trigger is configured in the checked-in upload metadata. Authorize recovery maintenance separately before unattended operation. A twice-daily recovery schedule is compatible with the 24-hour recovery window. The R2 lifecycle expires orphaned objects independently.

## Delivery and security boundaries

Cloudflare Email Routing must prepend the first receiver-owned `Authentication-Results` as documented. The Worker cross-checks it with the raw first header and requires applicable passing DMARC, a passing aligned DKIM signature linked by `header.d`, `header.s`, and `header.b`, and a matching signature covering the full raw body, From, Content-Type, and transfer encoding when present. Validate this exact metadata and actual MIME against the genuine synthetic delivery. The official public example simplifies the fields. If the platform or Instinct supplies insufficient metadata, leave the receiver closed while resolving the transport and continue using the supported offline file fallback. Avoid relaxing the check based on a From address. [Cloudflare receiver authentication](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/#authentication-results)

Domain-level verification cannot prove the managed account alone controlled a shared signing domain. The exact secret recipient limits submissions to parties who know it and meet mail authentication checks. It can leak in provider history, an email transcript, routing logs, headers, or a user action. It is revocable by replacing the rule and binding, and has no read, GitHub, R2 or publication privileges. Record the resulting trust as untrusted private intake. Use private operator-visible platform diagnostics for the first delivery. Keep message bodies, identifying headers, tokens, and the recipient out of repository files and Worker logs. If the provider view cannot supply the necessary data, use a separately approved, time-limited diagnostic route restricted to synthetic mail and record only field presence and pass/fail, then remove it.

A valid email has an immutable logical run ID and a stable signed transport delivery identity. The identity is bound to a validated report digest. New relay trace headers on the same delivery do not create another candidate. R2 rejects inconsistent reuse and writes candidate content before exposing the ready receipt. An interrupted write with durable candidate data is repairable by retry or scheduled recovery. An interruption before candidate data becomes durable requires identical redelivery. The system does not assume SMTP automatic redelivery or successful handoff. Malformed or suspicious submissions retain bounded reason metadata only. At the default limits there are 12 deliveries per UTC hour and four ingress-rejection receipts per hour. Conflicts found in the durable adapter count toward the overall admission cap. Flood exhaustion can delay legitimate reports. Check Routing/Worker errors and the dashboard's missed-run indicator together.

The private dashboard shows the 10 newest receipts in a 24-hour window. It distinguishes deliveries, last successful update, missing hourly deliveries after 90 minutes, partial reports, failed reports, and completed no-change checks. It labels validated report structure as pending review. Unreviewed reports, candidate claims, independently reviewed evidence and strategic interpretations, and public ledger entries have distinct trust states. S0 staging only displays untrusted submissions and their kinds. There is no write, promotion, or publication path and no staging editorial console. The separate public ledger remains synthetic in this phase.

## Qualification in order

1. In the approved project workspace, send **one** on-demand synthetic JSON email to the privately configured address using Instinct's managed sender. Use the completed example in the [agent contract](INSTINCT_AGENT_CONTRACT_v0.2.1.md), with a unique `run_id` and `report_type` set to `on_demand`.
2. Inspect the receiver-authentication and MIME result. Confirm actual envelope and From alignment, full-body signed MIME/encoding, Cloudflare's result and signature fields, and UTF-8 plain-text JSON before authorizing any real payload. When a field is absent, stop live qualification and inspect the specific failure.
3. Confirm one ready receipt with receiver time, raw content digest, pending review status, and durable candidate data. Bucket and projection must contain no raw MIME or rejected content.
4. With the existing protected preview open, verify that the report appears on focus or the next poll. Check the deployment SHA and initial Vercel build are unchanged. Run an unauthenticated API test and confirm Vercel's access challenge. Confirm the public ledger and fixture projection contain none of the submitted items.
5. Send the same synthetic JSON again, with the same run ID, using the supported native action. Verify one candidate and the expected receipt deduplication. Offline verification covers replay of the signed message itself and altered IDs.
6. Send the synthetic hourly `no_change` example. Verify it updates last successful time and adds no claims. Send a synthetic `partial` and `failed` example if validating all receipt states live.
7. From the same authorized native sender, send a deliberately invalid synthetic report, for example a body with a missing required field. Verify rejected delivery or a bounded metadata-only quarantine receipt with no report attached. Never include real data in the malformed test.
8. After these gates pass and permission for the specific source use and Instinct staging scope is confirmed, send one controlled report on permitted public sources. Check provenance and access controls. Review claims independently; leave public output unchanged.
9. Run a short authorized hourly trial, initially 24–48 expected deliveries, each with a stable unique ID and no-change receipts when warranted. Compare the Instinct task log, Cloudflare delivery and failure counts, and R2 receipts in UTC. Inspect latency, misses, duplicate/replay handling, CPU, and operator workload. This is delivery qualification. Use the prospective scientific evaluation before any release beyond staging.

## Kill switch and rollback

Disable the exact Cloudflare route and set `PULSE_STAGING_ENABLED=off` without changing MX for unrelated traffic. Pause the Instinct assignment in its approved workspace. When testing suspected disclosure, revoke the route address and Worker token, remove any preview bypass links, and delete or protect stale preview deployments as needed. Remove the branch-only Vercel staging flag and token for future preview builds. The Worker kill switch stops reads from existing preview builds immediately. Preserve authorized incident evidence privately, then apply retention. Re-enable only on a tested staging version after verifying the route, token, authentication and existing object compatibility. Use the previous compatible Worker version with its intake switch explicitly off during diagnosis. No production rollback is part of S0.

## Retention and cost

The default retention is 30 days and the adapter supports 7–90 days. Change the R2 lifecycle and Worker setting together. The recovery sweep prunes expired progress timestamps and can page through expired objects. Lifecycle independently clears orphaned candidate, receipt and delivery identity objects. Keep active aggregate progress out of backups, and delete it with the bucket when decommissioning. R2 object lifecycle deletion can lag; for a required immediate staging purge, stop intake, delete the bucket's data including progress using the scoped operator, and verify an empty listing or the bucket's removal. After expiration and deletion, an old signed delivery is no longer protected by its retired deduplication record. Retain only the window authorized for this pilot and rotate the address when retiring the route.

A 30-day month has 720 hourly, 30 daily, and four to five weekly runs before operator requests. At the maximum decoded payload this is about 48 MiB of input reports before modest object overhead, generally much less with hourly no-change receipts. Allow roughly 10,000 R2 writes and reads for typical uncontended intake and recovery. One visible dashboard for eight hours on 22 working days at five-minute idle polling generates about 2,100 requests, plus brief faster polling after activity. Conditional reads still list bounded receipt metadata and read a summary; 304s skip candidate body reads. Hidden sessions stop polling. These estimates fit within the published account-wide Standard R2 allowances of 10 GB-month, one million Class A and ten million Class B operations, assuming existing usage leaves room. [R2 pricing](https://developers.cloudflare.com/r2/pricing/)

Cloudflare lists inbound Email Routing as included, and Email Workers share the Workers Free limit of 10 ms CPU per invocation, 100,000 requests per day and 50 subrequests per invocation. Measure a representative large signed message and inbox reads on the eligible staging account before scheduling. R2 can be billable over its allowance. Existing domain, Vercel, and Instinct plan eligibility and capacity must be checked. The pilot targets zero incremental vendor spend. It requires no paid model calls, and any spending escalation remains an explicit owner decision. Budget about two to four operator hours for account setup and initial qualification once the domain and access exist, plus monitoring for the short reliability trial. [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/) · [Email Worker limits](https://developers.cloudflare.com/email-service/platform/limits/) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

Run ID and report state handling are receiver-owned. If real mail remains unavailable, run offline synthetic qualification and retain the manual import fallback. A dedicated project mailbox with a documented, authorized API could be a later transport. It would need its own receiver-attestation and replay validation. Personal mailboxes and speculative Instinct webhooks are outside this implementation.
